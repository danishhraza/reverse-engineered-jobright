# How Autofill Jobs works

A technical walkthrough of the code: what runs where, how a page gets filled, and how
differently worded questions on different sites map to the same answer.

## Tech stack

| Piece | What | Why |
| --- | --- | --- |
| Chrome extension, Manifest V3 | content script + service worker + side panel + options page | Runs inside the real, logged-in browser tab; no server needed |
| TypeScript (strict) | all source in `src/` | Types for profiles, fields and reports catch most mistakes at build time |
| esbuild | `scripts/build.mjs` bundles each entry point into one IIFE file in `dist/` | Fast (~20 ms), no framework, no runtime dependencies |
| `chrome.storage.local` | profiles, settings, learned answers, resume PDFs (as data URLs) | The "database": free, local, survives restarts. `unlimitedStorage` lifts the 10 MB cap for PDFs |
| `chrome.storage.session` | latest fill report per tab/frame, learned answers awaiting approval | Cleared when the browser closes |
| vitest + jsdom | `tests/` | Simulated Greenhouse/Workday/SuccessFactors pages, including slow dropdowns and uploads |

No LLM, no backend, no UI framework. The only runtime code is what's in `src/`.

## The three runtimes

A Chrome extension is three separate JavaScript worlds that talk by messages:

```
 side panel / floating button / Alt+Shift+F
          │  {type:'fillTab', mode}
          ▼
 background.ts (service worker)
          │  webNavigation.getAllFrames(tab) → {type:'fill'} to EVERY frame
          ▼
 content/index.ts (one copy per frame)        ← the form is often inside an iframe
          │  run() / runSingle()               (Greenhouse embedded in a careers page)
          │  {type:'report'} after each field
          ▼
 background.ts ── stores it in storage.session, relays it to the top frame's button
          ▼
 side panel re-renders
```

- **Content script** (`content/index.ts`) is the only part that can touch the page. It is
  injected into every frame (`all_frames: true`). Each frame decides for itself whether it
  has a form. Until you press Fill it only *reads* the page (see "Being invisible" below).
- **Background** (`background.ts`) has no DOM. It fans messages out to frames, keeps the
  latest report per frame so the side panel can show it when opened later, handles keyboard
  shortcuts, and queues learned answers.
- **Side panel / options** are ordinary extension pages reading and writing `chrome.storage`.

Fill modes travel with the message: `all` (overwrite), `empty` (skip anything that has a
value), `focused` (background asks each frame `focusInfo` for when you last clicked a field,
and only the most recent frame fills just that field).

## Profiles

`profiles/*.json` is a `ProfileStore`:

```jsonc
{
  "base": { "personal": {...}, "education": [...], "eeo": {...}, "preferences": {...}, "answers": [...] },
  "profiles": [
    { "id": "swe", "name": "SWE", "overrides": { "headline": "...", "work": [...], "skills": [...] } }
  ]
}
```

`resolveProfile(store, id)` in `profile/merge.ts` builds the effective profile:
`EMPTY ← base ← overrides`. Objects merge key by key, arrays *replace* (so a profile's
`work` list fully replaces the base one), and answer banks concatenate (profile entries
first, so they win). The resume PDF for each profile is stored separately as
`resume:<id>` so the profile JSON stays small and exportable.

## Filling a page, step by step

`run()` (`engine/run.ts`) loops over pages; `fillPage()` (`engine/fill.ts`) does one page:

1. **Wait for the page to settle.** `waitForSettle()` uses a `MutationObserver` and resolves
   once the DOM has been quiet for 400 ms. Many ATS pages are still rendering when you click.
2. **Resume first.** Sites like Workday parse the uploaded resume and overwrite fields, so the
   resume goes in before anything else. The file input is found by the adapter or by scoring
   file inputs whose label mentions resume/CV (cover-letter inputs score negative). If there is
   no file input yet (SuccessFactors creates it when you click "Upload"), it clicks the
   Upload/Attach button next to the word "Resume" while a capture-phase click listener blocks
   the OS file picker, then uses the input that appears. The PDF is attached with a
   `DataTransfer` object (the only way to set `input.files` from script), then it waits for the
   site to show the filename or a success marker, then waits for the parsing to settle.
3. **Adapter sections.** `adapter.fillSpecial()`, e.g. Workday's repeatable panels: find the
   "Work Experience" heading, click **Add** until there are enough "Work Experience N"
   panels, and fill each panel from `profile.work[N-1]`.
   Sites without their own adapter code get the same from `sections.ts`: a section runs from a
   title like "Work History" or "Education" to its **add another** link, in document order.
   Blocks inside it are split where a label repeats (a second "Employer" starts job 2). Block N
   is filled from entry N of the profile, and the link is clicked until there's a block per
   entry. Each block gets two rounds, because an answer can reveal fields ("Current position?
   No" → End Date). A field the entry doesn't cover goes to the generic engine (e.g. "Highest
   degree obtained"). This is plain order matching, no LLM.
4. **Generic passes.** `scanFields()` → for each field not handled yet: `classify` → `resolve`
   → `fillField`. Then scan again, because answering one question often reveals another
   ("Yes, I need sponsorship" → "Which visa?"). It keeps going until a scan finds nothing new,
   then keeps watching for 5 more seconds for late-rendering sections.
5. **Report.** Every field becomes a `FieldReport` row: `filled`, `flagged` (needs you),
   `skipped` or `failed`, with a confidence score and a reason.

Back in `run()`: stop if this is the review/submit page, if a required field is flagged, or if
the site shows validation errors; otherwise click **Next**, wait for the page signature
(Workday's active progress step, else the page heading, else the URL) to change, and repeat. It never clicks Submit.

## How it finds fields (`engine/fields.ts`)

`scanFields()` walks the DOM once and produces a flat list of `Field` objects:

| Kind | How it's recognized |
| --- | --- |
| `combobox` | `role="combobox"`, `aria-haspopup="listbox"`, `aria-autocomplete`, Workday `multiselectInputContainer`. Scanned first so its inner `<input>` isn't also counted as a text box |
| `text`, `textarea`, `date`, `select` | native elements |
| `richtext` | `contenteditable` editors (Quill, Draft.js, ProseMirror) |
| `radio` | radios grouped by `name` (or by their fieldset/radiogroup) |
| `checkbox`, `checkboxGroup` | a lone checkbox, or several sharing a `name` |
| `buttonGroup` | a parent with 2–5 buttons including exactly "Yes" and "No" (Ashby). The hidden checkbox Ashby keeps behind them is skipped |
| `file` | file inputs, even when hidden behind an "Attach" button |

Hidden fields, honeypots and captchas are skipped. Each field gets a `data-rej-id` attribute
so the side panel can scroll to it later.

### Reading the question text

The hard part is not finding the input, it's reading the *question* a human would read next
to it. `labelFor()` tries, in order:

1. Workday's wrapper: `[data-automation-id^="formField-"]` → its `<label>`
2. `aria-labelledby` → text of the referenced elements
3. `<label for=…>` / wrapping `<label>` (preferring a child with "label" in its class, which
   strips Lever's helper text)
4. `aria-label`
5. Text immediately before the field (walking previous siblings and up a few parents)
6. `placeholder`

If what it found is just a button word ("Attach", "Upload", "Browse"), it looks outward to the
group's label instead. Radio/checkbox groups use the `<legend>` or radiogroup label.
Required = `required`, `aria-required`, or a `*`/`✱` in the label (stripped afterwards).

It also collects **hints**: `name`, `id`, `data-automation-id`, `autocomplete`, `data-qa`,
split from camelCase (`legalNameSection_firstName` → `legal name section first name`). Hints
are a weaker fallback when the label is missing or unhelpful.

## How differently named fields map to the same answer (`engine/answers.ts`)

Different sites ask the same thing many ways: "Legal first name", "Given name", "First Name *",
`data-automation-id="legalNameSection_firstName"`. The pipeline:

**1. Normalize.** `norm()` lowercases, strips accents and punctuation, `&` → `and`:
`"Are you legally authorized to work in the U.S.?*"` → `"are you legally authorized to work in the u s"`.

**2. Classify: question → a key.** In priority order:

| Source | Score | Example |
| --- | --- | --- |
| Learned answer, exact question match | 0.90 | you answered "Do you have a clearance?" once |
| Answer bank (profile `answers`), questions of 3+ words | 0.88 | pattern `non-compete` → `No` |
| Rule on the label, short label (≤7 words) | 0.92 | `"Given name"` → `firstName` |
| Rule on the label, long sentence | 0.85 | `"Will you now or in the future require sponsorship…"` → `sponsorship` |
| Rule on the hints only | 0.70–0.75 | `name="fname"` with no label → `firstName` |

The rules are an **ordered** list of regexes, most specific first. Order is what stops
"Preferred first name" from matching `firstName`, "Institution City" from matching your home
`city`, and "Country phone code" from matching `country`:

```ts
{ key: 'preferredFirstName', label: /\b(preferred|nick) ?(first )?name\b/ },
{ key: 'firstName', label: /\b(first|given|fore) ?name\b/, attr: /\bfirst ?name\b|\bfname\b/, short: true },
...
{ key: 'schoolCity', label: /\b(institution|school|university|college)\b.*\b(city|location)\b/, short: true },
{ key: 'location', label: /\blocation\b|where are you (currently )?(located|based)/, not: /willing|relocat/ },
{ key: 'city', label: /\bcity\b|\btown\b/, short: true },
```

- `short: true` means "only for field-name-like labels". It stops a long question that happens
  to contain "city" from being treated as the City field.
- `not:` excludes look-alikes ("Are you open to our *location* in Austin?" is not the Location field).
- Answer-bank patterns are plain words (all must appear) or `/regex/`.

**3. Resolve: key → your answer.** `resolve()` reads the profile and returns one of:

- `{desired}`: what to put in, with alternates: `text: "United States"`,
  `alts: ["United States of America", "USA", "US"]`. Yes/No questions carry `bool`;
  "prefer not to say" answers carry `decline`.
- `{flag}`: ask the human. Examples: ethnicity left `null`; a work-authorization question
  naming a country you have no entry for ("Are you a Singapore citizen?"); consent boxes.
- `{skip}`: nothing to put (no middle name, optional cover letter).

Some keys need context: "Highest level of education **obtained**" skips an in-progress
degree; "Institution City" reads the school's city; job descriptions become
`• bullet` lines.

**4. Match the option (`engine/match.ts`).** For dropdowns, radios and button groups the site
offers its own wording, so `matchOption(options, desired)` scores each option:

| Case | Score |
| --- | --- |
| Exact (after `norm`) | 1.0 |
| One starts with the other | 0.9 |
| Option contains the answer as whole words | 0.85 |
| Answer contains the option | 0.8 |
| Otherwise word overlap (Jaccard) × 0.8 | 0–0.8 |

Yes/No answers also accept "yes-ish" and "no-ish" sentences ("I am authorized…",
"I do not require…", "I am not a protected veteran"), and `decline` picks
"I don't wish to answer" / "Prefer not to say". Placeholders ("Select…", "Loading…") are
ignored. If two options tie and neither is exact, confidence is capped at 0.55, because a
coin flip shouldn't count as sure.

**5. Decide.** Final confidence = classification score × match score:

- below 0.55 → don't fill, flag it
- 0.55–0.75 → fill it but flag it "check this"
- above 0.75 → filled
- any option match below 0.6 is rejected outright

## How each widget is filled (`engine/widgets.ts`, `engine/dom.ts`)

Sites are built with React/Vue/Angular, which ignore `input.value = 'x'`. So:

- **Text:** call the *native* `value` setter from `HTMLInputElement.prototype` (bypassing
  React's override), then fire `input`, `change` and `blur`. Then read the value back. Phone
  masks that reformat the number are accepted if the digits survived.
- **Native select:** match the options, set `value` the same way.
- **Custom dropdowns** (react-select, Workday prompts): click the trigger with a full
  `pointerdown → mousedown → focus → pointerup → mouseup → click` sequence (many widgets only
  listen to `mousedown`), type a query, wait up to 2.5 s for options to appear (Workday also
  needs **Enter**), wait for the list to stop changing ("Loading…" → results), pick the best
  match, then verify the displayed value. Queries are tried in order: the answer, a shorter
  form, an alternate, and finally an empty query to see the whole list. Two levels of nesting
  are followed (Workday: "Job Board" → "LinkedIn").
- **Tag pickers** (skills): one skill at a time. Type it, wait up to 6 s for the site's
  search (or stop early on "No results"), pick only a close match (shortest label wins a tie,
  so "React" picks "React.js" over "React Native", and never "Reactor"), then check a chip
  appeared. It never presses Enter, which on many pickers selects whatever is highlighted.
- **Radio / Yes-No buttons:** match, click, verify `checked` / `aria-pressed`.
- **Rich text:** dispatch a synthetic `paste` event (every major editor handles paste and keeps
  line breaks), fall back to `execCommand('insertText')` line by line, then to `<p>` per line.
- **Waiting:** `waitFor(fn)` re-checks on every DOM mutation and on an interval;
  `waitForSettle()` waits for quiet. Both return early on Cancel.

Non-dropdown fields get 3 tries with a growing pause; dropdowns get 1, since they already try
several queries internally.

## Site adapters (`src/adapters/`)

The engine is generic; an adapter adds only what a site does differently:

```ts
interface Adapter {
  detect(location, document): boolean;        // hostname or a telltale element
  resumeInput?(): HTMLInputElement | null;    // the right file input
  waitResumeProcessed?(input, file): Promise<boolean>;
  fillSpecial?(ctx): Promise<void>;           // e.g. Workday Work/Education panels
  fillOne?(ctx, field): Promise<FieldReport | null | undefined>;  // single-field fill inside those panels
  nextButton?(), isFinalPage?(), pageSignature?(), hasErrors?()   // multi-page forms
}
```

`pickAdapter()` checks Workday, Greenhouse, Ashby, Lever, then falls back to Generic, which works
on most other forms (SuccessFactors, iCIMS, company sites) because everything above is
site-independent.

## Learning, progress, cancel

- **Learning.** After a fill, flagged *question* fields (3+ words, never passwords/SSN/DOB) get
  `change`/`blur` listeners. When you answer one, the content script compares it to what's
  already saved and sends a proposal. The background queues it in `storage.session` (latest
  answer per question wins) and puts a count badge on the toolbar icon. The side panel shows
  each one with ✓ (save, replacing any old answer) and ✕. Saved answers are matched by exact
  question text at score 0.9.
- **Progress.** `control.ts` holds a `status()` sink. The engine calls
  `status('Picking "Country" — waiting for its options…')` at each step; `run()` turns that
  into a report with a `current` line, shown in the side panel and on the floating button.
- **Cancel.** `cancel()` sets a flag. `checkCancel()` between fields/sections/pages throws a
  `Cancelled` error that `run()` catches, and every wait returns early when the flag is set, so
  it stops within about 100 ms even mid-dropdown. Catch blocks meant for real errors call
  `rethrowCancel()` so they don't swallow it. The content script also sends a "Stopped"
  report the moment you press Cancel, so the side panel doesn't wait for the engine to unwind.
- **Pages that reload mid-fill.** A full page load kills the content script and its run.
  Before any click that may reload the page (Next, an "upload my resume" choice, an Upload
  button) the page sends `advancing` to the background, which keeps it in session storage for
  30 s. If the tab then finishes loading, the background starts the fill again with the next
  page number. Any other reload (`webNavigation.onCommitted`) closes out the frame's report as
  done. Cancel with nothing actually running does the same, and the side panel treats a fill
  that's been silent for 60 s as stopped.
- **Job site login.** `account` in `chrome.storage.local` (email, optional user name,
  password), merged into the profile at fill time. A `type=password` input is always the
  password; on a page that has one, email fields get the login email. Password values are
  masked as •••••••• in reports and never learned.

## Being invisible until you press Fill

Before you press Fill, the content script must not change the page. React/Next.js sites compare
the DOM against what they expect while hydrating, and an extension adding attributes or nodes
too early can break the page. So:

- passive form detection (`looksLikeForm()`) only *reads*: counts visible inputs, no stamping;
- the floating button is added only after the `load` event, a quiet DOM, and an idle callback;
- focus tracking for "just the field I clicked" is a passive `focusin`/`pointerdown` listener.

## Testing

`npm test` runs vitest in jsdom:

- `match.test.ts`, `classify.test.ts`: option scoring and question → key on real wording seen
  on live Greenhouse/Lever/Ashby/SuccessFactors forms (regressions included).
- `fill.test.ts`: simulated Greenhouse page (async location dropdown, delayed upload, Ashby
  Yes/No buttons), SuccessFactors-style late section + Upload button, dropdown that never
  matches, Workday-style multi-page with Add panels stopping at Review.
- `modes.test.ts`: only-empty, single-field (including radio labels and "not a field"),
  rich-text bullets, and that passive detection never modifies the page.
- `cancel.test.ts`: progress lines appear and Cancel stops mid-dropdown, then a new fill works.
- `live-scan.test.ts`: `LIVE_HTML=page.html npm test` prints how each field on a saved real page
  is classified. Use it when a site misbehaves.

`tests/setup.ts` polyfills `DataTransfer` and settable `input.files`, which jsdom lacks.
